## 1. Goal

Give the **super admin** everything needed to run the platform without touching the database:
create clinics (provisioned from the template), manage them, and manage each clinic's roles and staff.

**Done when:** the super admin creates a clinic from the admin area, and its owner logs in and sees
the drugs and groups copied from the template.

## 2. Business

Only the super admin uses M1.5. Clinics cannot manage their own staff or roles yet, but the screens and
use cases are built so they can later.

| Area | What the super admin can do | Rules |
|---|---|---|
| **Template** | Edit the default drugs and groups (already possible: the "Template clinic" context, HLD 7.5). M1.5 links to it from the admin area and seeds it with sample content in Development | Later template edits don't change existing clinics |
| **Create clinic** | Name + owner phone + owner name, one form | One transaction: clinic → default roles (Owner, Doctor, Assistant) → owner as staff with the Owner role (existing user reused by phone) → copy of the template's drugs and groups. All or nothing |
| **Clinics** | List, search, filter by status, open, rename, **disable** (suspend) / **enable**, **delete** | Disabled: nobody can enter, data kept. Deleted: **soft delete**, final for now (no restore UI), hidden everywhere, nobody can enter. The template can't be renamed, disabled or deleted |
| **Roles** (per clinic) | List, create, edit (name + permissions, grouped by module), delete | Picking a permission adds what it requires. Name unique in the clinic. **Owner** role: locked (can't be edited or deleted), always all permissions. A role in use can't be deleted |
| **Staff** (per clinic) | List, search, add by phone (name + roles), edit (name, roles, active), remove | One staff row per person per clinic. At least one role. A clinic always keeps **one active Owner** at least |
| **Lockout** | — | Disabling or deleting a clinic, deactivating or removing a staff member, or changing a role takes effect on their **next request** |

Only clinics are soft-deleted; staff, roles, drugs and groups keep real deletes (user's decision, 2026-10-14).

## 3. What existed before M1.5

The baseline the decisions start from (kept as written then); see § 4–9 for what was built.

| Piece | State |
|---|---|
| `Clinics` table | `Name`, `Status` (`active`/`suspended`), `IsTemplate` (one, partial unique index), timestamps |
| Template clinic | Created at startup; **empty**. The super admin can enter it (context `clinic`, `isTemplate`) and has every permission there |
| Dev seed (`StartupSeeder`, Infrastructure) | On an empty dev DB: "Demo clinic" (10,000 drugs) and "Second demo clinic" (3 drugs, 1 group, a read-only "Viewer" role), created **directly**, not by provisioning (before M1.5.2; see D6) |
| `DefaultRoles.SeedAsync` | Creates Owner/Doctor/Assistant in a clinic (clinic context must be that clinic). Since M1.5.2 `DefaultRoles` holds only the names and permissions; `DefaultRolesSeeder` creates the roles (D5) |
| Access checks | Per request, cached (`IAccessCache`, HybridCache with tags): staff active + clinic `active`, else 403 `noAccess`/`clinicSuspended`. `Invalidate{Staff,Role,Clinic,User}Async` exist; only token issuing (`SessionService`, inside its transaction) and the super-admin seed call them |

| Frontend | `RequireAuth context="platform"`, `<Can>`, `RequirePermission`, `PERMISSIONS`; a template banner in `AppLayout` |

## 4. Decisions

Each one is a short ADR: context → decision → why (and the options not taken).

### D1. Admin authorization: a `PlatformAdmin` policy (not permissions)

- **Context:** admin endpoints act across clinics. Platform-context tokens have no staff row and `/me`
  permissions are `[]`.
- **Decision:** a new policy `AuthPolicies.PlatformAdmin`: authenticated, `ctx = platform`, and the user is
  **still** a super admin (`IAccessCache.GetUserAsync`, so removing a phone from `SuperAdminPhones` locks it out
  on the next request). Failure → 403 `forbidden`. Every `/admin/*` controller has it.
- **Why:** one super admin role today; platform permissions (several admin users with different rights)
  can come later as `platform.*` keys without changing the endpoints' shape.
- **Not taken:** `[HasPermission]` with platform keys now (no platform roles exist to hold them).

### D2. "The current clinic" is set at the edge; use cases never take a clinic id

- **Context:** role and staff use cases must run **inside a clinic** (the query filter and the save
  interceptor need `IClinicContext`). Staff tokens carry their clinic; the super admin's token has none.
- **Decision:** role and staff commands and queries carry **only the ids they need** (`UpdateRole(roleId, …)`),
  never a clinic id, and work in the request's current clinic, exactly like the Catalog use cases today.
  Who sets the current clinic:

  | Caller | Source of the current clinic |
  |---|---|
  | Staff / owner (clinic-side, after the MVP) | the token (existing middleware, nothing new) |
  | Super admin, `/admin/clinics/{clinicId}/roles…` and `/staff…` | an **admin clinic filter** on those controllers (Api): it calls `IClinicScope.EnterAsync(clinicId)` (Application), which answers `ClinicErrors.NotFound` (404 `notFound`) for a missing, **deleted** or **template** clinic, else sets the current clinic for the request. A **suspended** clinic is allowed: the super admin manages it |
  | Non-HTTP code (provisioning, dev seed) | `using (scope.Use(clinicId)) { … }`: a block inside a clinic, restoring the previous one after |

  `EnterAsync` refuses to switch to a different clinic once one is set (a request never changes clinic
  halfway); the policy (D1) already guarantees admin requests start with none. The pipeline is unchanged
  (Logging → Validation → Transaction).
- **Clinic use cases** (get, rename, suspend, activate, delete): the clinic **is** their target, so they take
  its id like any other entity id and look it up with `Clinics.NotDeleted()` excluding the template (404 otherwise).
- **Cross-clinic work** (super admin only, Platform module): reads across clinics are explicit
  (`IgnoreQueryFilters()`, allowed only in Platform code, HLD 4.1: the clinic list with staff counts, later
  "which clinics is this phone in?"); writes go **one clinic at a time** through `scope.Use(clinicId)`
  (provisioning: read the template, write the new clinic; later e.g. "add a drug to every clinic"). The save
  interceptor refuses any row of another clinic than the current one, so a cross-clinic write can't spill.
- **Why:** commands stay small (no clinic id everywhere); isolation keeps working by construction (role and
  staff handlers never bypass the filter); clinic-side endpoints later send the very same commands, the
  clinic coming from the token.
- **Not taken:** a `ClinicId` on every command + a pipeline behavior (every future command would carry it;
  more to get wrong); `IgnoreQueryFilters()` + explicit `ClinicId` in each handler (one forgotten check = a leak).

### D3. Cache invalidation **after commit**: `IPostCommitActions`

- **Context:** invalidating the access cache inside the transaction leaves a window: a concurrent request
  reloads the **old** rows (not committed yet) and caches them for up to 10 minutes.
- **Decision:** a scoped `IPostCommitActions` (Application, `Common/Abstractions`; implemented by
  `TransactionRunner` itself, one instance per request for both interfaces): handlers call
  `await postCommit.AddAsync(token => accessCache.InvalidateStaffAsync(id, token))`. `TransactionRunner` runs the queue
  **when the outermost transaction it opened ends, committed or rolled back**, after the execution strategy has
  finished (retries included): clearing a cache entry is always safe (worst case one extra reload), so there is
  no rollback bookkeeping, also for nested commands (savepoints only queue). Called with no transaction opened
  by the runner, `AddAsync` runs the action at once (hence async). A failing action is logged, not thrown; actions
  get `CancellationToken.None` (the commit may have happened even if the request was cancelled). Code that opens
  its own transaction outside `TransactionRunner` (the dev seed) must not rely on it: inside such a transaction
  `AddAsync` runs at once, before that commit (nothing it seeds is cached yet).
- **Accepted for the MVP:** a cache load that **started before** the commit (a request of that same staff
  member, in the same few milliseconds) could finish after the invalidation and store the old row; the change
  then takes effect when the entry expires (≤ 10 min) instead of at once. Nothing is built for it.
- The existing call in `SessionService.IssueAsync` (invalidate staff + user when a token is issued) moves to
  `IPostCommitActions` too: it has the same window today.
- **Why:** correct ordering in one place; handlers can't get it wrong. Reusable for later side effects
  (e.g. sending an SMS after commit, carry-over item in architecture.md).
- **Not taken:** invalidate before and after commit (double work); domain events (heavier than needed).

| Change | Invalidate (after commit) |
|---|---|
| Clinic disabled / enabled / deleted | `InvalidateClinicAsync(clinicId)` (a rename needs none: no cached entry holds the name; contexts read it from the database) |
| Role permissions or name changed | `InvalidateRoleAsync(roleId)` |
| Role deleted | `InvalidateClinicAsync(clinicId)` (its staff's role lists change) |
| Staff added / edited (name, roles, active) / removed | `InvalidateStaffAsync(staffId)` |

### D4. Clinic soft delete = a `DeletedAt` column (user's decision)

- **Context:** delete must hide the clinic everywhere and lock everyone out, keep all its rows, and be
  restorable later by a future feature.
- **Decision:** a new nullable `Clinics.DeletedAt` (migration `AddClinicDeletedAt`, added on top). Deleted
  = `DeletedAt` is set. `Status` keeps its meaning (`active` / `suspended`) and is not touched by a delete, so a
  future restore just clears `DeletedAt` and the clinic comes back in the state it had. Final in M1.5 (no
  endpoint clears it).
- **Every place that decides whether a clinic can be used checks it explicitly** (there are few, all known):

  | Place | Change |
  |---|---|
  | `MembershipService.GetEnterableClinicsAsync` (login contexts, refresh, switch) | + `DeletedAt == null` |
  | Cached access check (`AccessCache` staff and clinic entries) | entries carry the flag (`StaffAccess.IsClinicDeleted`, `ClinicAccess.IsDeleted`); `PermissionService` answers `noAccess` for it, checked before the status (not `clinicSuspended`, which would reveal the clinic) |
  | Context switch "is it suspended?" check | a deleted clinic answers `noAccess`, whatever its `Status` |
  | Admin clinic filter (`IClinicScope.EnterAsync`, D2) and the clinic use cases | deleted → 404 |
  | Admin queries | one helper, `Clinics.NotDeleted()` (`Platform/Clinics/ClinicQueries`), used by every admin list and lookup; `Clinics.Manageable()` = `NotDeleted()` without the template |

- **Not taken:** an EF global query filter on `Clinics` (`DeletedAt == null`): the access reads bypass filters
  with `IgnoreQueryFilters()` (which would also bypass this one, silently) and the cached access query reads
  the clinic's row itself (a join) to carry the flag. Explicit checks in the five places above are
  easier to see and review.

### D5. Provisioning: `IClinicProvisioner` + ordered `IClinicSeeder`s

- **Context:** HLD 7.3. The dev seed and the create-clinic use case must provision the same way; later
  modules (M2.1 dynamic forms) add their own seeding step.
- **Decision:**
  - `IClinicProvisioner.ProvisionAsync(name, ownerPhone, ownerName)` (Application, `Features/Platform/Provisioning`,
    **internal**): inserts the clinic, then inside `scope.Use(newClinicId)` runs every registered `IClinicSeeder`
    in `Order` and builds the returned `ClinicDetails` (owners are clinic-owned rows, read inside the scope). Only the `CreateClinicCommand` handler calls it, so it always runs inside that
    command's transaction (`TransactionBehavior`); the provisioner itself never deals with transactions.
    Everyone who creates a clinic, the dev seed included (D6), sends `CreateClinicCommand`.
  - Seeders (each its own class, registered as `IClinicSeeder`): `DefaultRolesSeeder` (10, creates
    the `DefaultRoles`), `OwnerSeeder` (20, the owner's `User` by phone + `Staff` with the Owner role),
    `TemplateCatalogSeeder` (30, copy drugs, then groups + items with drug ids remapped).
  - Finding or creating a user by phone is shared with "add staff" (M1.5.3): `IUserAccounts.GetOrCreateAsync(phone)`
    in `Identity/Users` (the phone already normalized). It replaces `IIdentitySeeder.EnsureUserAsync` (the
    dev seed uses it too), so there is one way to find or create a user by phone. Two requests creating the same new phone at the
    same moment hit the unique index: one fails with 500 and simply works when sent again (accepted for the
    MVP: one super admin).
  - The catalog copy reads the template with `IgnoreQueryFilters()` + `ClinicId == templateId`, `AsNoTracking`,
    and builds **new** entities, including new `Dosing` instances (an owned instance can't be shared).
  - `CreateClinicCommand` (handler → provisioner) runs in one transaction (`TransactionBehavior`): any failure
    rolls everything back.
- **Why:** one provisioning path; a new module adds a seeder without touching the others; transactions stay
  the pipeline's job (architecture § 3.5), so no "am I in a transaction?" check is needed.
- **Limits:** EF copy in memory is fine for templates of hundreds of drugs; if a template ever holds thousands,
  move the copy to SQL behind a purpose-built interface (architecture § 3.6).
- **Built (M1.5.2), details this section left open:** `ClinicSeedContext(ClinicId, OwnerPhone, OwnerName)` only; the
  `OwnerSeeder` reads the new clinic's Owner role from the database (query filter) instead of receiving it from the
  roles seeder. A request without `owner` → 400 `invalidRequest` (field `owner`); the owner's `fullName` uses the
  name rules (`nameRequired`, `nameInvalid`, `nameTooLong`). Config phones (super admins, dev seed) are normalized by the caller
  with `ConfigPhones.Normalize` (invalid → startup error naming the setting), then passed to `IUserAccounts`.
  No cache invalidation after a create (all the cached keys involved are new ids; an existing owner's contexts are
  read from the database). Also accepted (MVP, one super admin): a drug and a group using it saved in the template
  between the copy's two reads (drugs, then groups) → 500, rolled back; no lock.

### D6. Dev seed goes through provisioning; the template gets sample content

- **Decision:** on an empty dev DB the `StartupSeeder`:
  1. fills the **template** with the **smallest content that proves the copy**: two drugs and one group using
     both (one line with a dosing override). The user then replaces it with the real catalog through the
     template context;
  2. creates **"Demo clinic"** (owner `DevOwnerPhone`) by sending `CreateClinicCommand` (`ISender`), then adds
     the 10,000 bulk drugs directly (for paging and search checks) and the Assistant (`DevAssistantPhone`);
  3. creates **"Second demo clinic"** (same owner) the same way, then adds the read-only "Viewer" role and the
     assistant as Viewer.

  The seed keeps its own "all or nothing" transaction; the commands it sends join it (`TransactionRunner`
  already joins an open transaction through a savepoint).
- **Built (M1.5.2), additions:** the template fill is skipped when the template already has drugs (e.g. added by hand
  before the demo clinics exist, or on an earlier start without `DevOwnerPhone`); an empty `DevOwnerPhone` skips only
  the demo clinics with a warning (a clinic needs an owner; the template is still filled when empty). Template
  content: "Moxifloxacin 0.5%" and "Prednisolone acetate 1%" with default dosings, group "After cataract surgery", the
  Prednisolone line overriding with a taper and the eye asked.
- **Why:** the dev seed exercises the exact path the admin screen uses, on every fresh dev DB; dev phones and
  roles stay as today, so existing manual checks keep working.

### D7. No session revocation in M1.5

- **Context:** HLD 7.6 planned "revoke the sessions" on suspend/remove. Since M1.3 every clinic request
  re-checks access (cached + invalidated), and refresh/switch re-check the contexts.
- **Decision:** don't revoke sessions. Disable/delete/deactivate/remove take effect on the next request
  (403, then the SPA refreshes the session and `/me` and the user lands on the context picker or login, or in their
  only other clinic with a message). HLD 7.6 is updated.
- **Why:** same user-visible result with no extra write path; revocation can be added with the audit log.

### D8. Permissions: no new keys in M1.5; reuse `GET /permissions`

- **Decision:** don't declare `roles.*`/`staff.*` yet: no clinic-side endpoint would use them, and a role
  holding them would grant nothing. They come with the clinic-side screens (after the MVP). The role editor
  reads the existing `GET /permissions` (the HLD's `/admin/permissions` is dropped).
- Role save stores the picked keys **completed with their requirements** (`PermissionCatalog.WithRequirements`);
  unknown keys → 400 `unknownPermission`.

### D9. Frontend: reusable role and staff components with a data adapter

- **Decision:** `features/roles` and `features/staff` hold components that never build URLs:
  `RoleList`, `RoleEditorDialog` (permission picker grouped by module → resource, auto-adds requirements,
  shows why a box is locked), `StaffList`, `StaffEditorDialog`. They take an **adapter** (TypeScript interface:
  `list`, `create`, `update`, `delete`, plus a query-key scope). M1.5 passes `adminRolesApi(clinicId)` /
  `adminStaffApi(clinicId)`; a clinic-side route later passes `clinicRolesApi()` and wraps them in
  `RequirePermission`.
- `features/admin` holds the admin shell and the clinic pages only.
- **Built (M1.5.5), details this section left open:** the adapters are `RolesAdapter` / `StaffAdapter`
  (`features/roles/types.ts`, `features/staff/types.ts`) on a shared `DataScope` (`api/dataScope.ts`): `scope` (the query-key
  prefix), `affects` (other cached data a change also changes, reloaded after it) and `container` (the clinic's details,
  reloaded when a tab's data answers 404, so the page shows "not found"). `adminRolesApi(clinicId)` /
  `adminStaffApi(clinicId)` live in `features/admin/adapters.ts` (they know the admin URLs and the clinic's cache keys). The
  components hold no route: `RoleList({adapter})`, `StaffList({adapter, rolesAdapter})` (the staff editor picks from the
  clinic's roles), each with its own create/edit dialog and delete confirm. The tabs (`ClinicRolesTab`,
  `ClinicStaffTab`) only build the adapters for the page's clinic. D9 holds for the data, not yet for the actions: the
  components always show Add / Edit / Delete and the staff editor always lists the roles; per-action gating (`<Can>`
  or capability flags on the adapter) comes with the clinic-side screens.

## 6. API (`/api/v1/admin`, policy `PlatformAdmin`)

| Method | Route | Request | Response / errors |
|---|---|---|---|
| GET | `/admin/clinics?search&status&page&pageSize` | | `PagedResult<ClinicSummary>` (no template, no deleted; `status` = `active`/`suspended`) |
| GET | `/admin/clinics/{id}` | | `ClinicDetails`; 404 `notFound` |
| POST | `/admin/clinics` | `{ name, owner: { phone, fullName } }` | `201 ClinicDetails`. `nameRequired`, `nameInvalid`, `nameTooLong`, `invalidPhone` (+ `invalidRequest` without `owner`, built) |
| PUT | `/admin/clinics/{id}` | `{ name }` | `ClinicDetails` |
| POST | `/admin/clinics/{id}/suspend` · `/activate` | | `204` (idempotent) |
| DELETE | `/admin/clinics/{id}` | | `204`; soft delete, final |
| GET | `/admin/clinics/{id}/roles` | | `Role[]` (Owner first, then by name) |
| POST | `/admin/clinics/{id}/roles` | `{ name, permissions[] }` | `201 Role`. `nameRequired`, `nameInvalid`, `nameTooLong`, `roleNameTaken`, `unknownPermission` |
| PUT | `/admin/clinics/{id}/roles/{roleId}` | `{ name, permissions[] }` | `Role`. + `roleLocked` (Owner) |
| DELETE | `/admin/clinics/{id}/roles/{roleId}` | | `204`. `roleLocked`, `roleInUse` |
| GET | `/admin/clinics/{id}/staff?search&page&pageSize` | | `PagedResult<StaffMember>` |
| POST | `/admin/clinics/{id}/staff` | `{ phone, fullName, roleIds[] }` | `201 StaffMember`. `invalidPhone`, `nameRequired`, `nameInvalid`, `staffExists`, `rolesRequired`, `roleNotFound` |
| PUT | `/admin/clinics/{id}/staff/{staffId}` | `{ fullName, isActive, roleIds[] }` | `StaffMember`. + `lastOwner` |
| DELETE | `/admin/clinics/{id}/staff/{staffId}` | | `204`. `lastOwner` |

Every `{id}` that is missing, deleted or the template → 404 `notFound` (D2). Role and staff ids from another
clinic → 404 (the clinic filter hides them). A clinic's `staffCount` counts active staff; a role's `staffCount` counts
every staff row holding it, active or not (what `roleInUse` checks; decided in M1.5.3). A staff member's phone can't be
changed (remove and add again; changing a user's phone is out of the MVP). `lastOwner` guards every path that
could leave the clinic without an active Owner: deactivating, removing, or taking the Owner role away.
**Accepted for the MVP:** the `lastOwner` and `roleInUse` checks read, then write; two changes in the very same
instant could both pass (e.g. two tabs each removing a different Owner). With one super admin this is not
guarded (no lock); revisit when clinics manage their own staff.

**Built (M1.5.3), details this section left open:** the filter is `[AdminClinic]` (`Api/Features/Platform/AdminClinicFilter.cs`,
a resource filter: after authorization, before model binding, so an unknown clinic answers 404 even with a malformed
body). A role's `permissions` for the Owner = every catalog key (it stores none); others in catalog order. Role names:
`ValidName` with the role column's limit (`FieldLimits.RoleNameMaxLength`, 100; `ValidName` took a max-length
parameter, default 256), unique **case-insensitively** after trimming (stricter than the exact `(ClinicId, Name)` index,
which then only catches a same-instant race: 500). `permissions: []` is allowed (a role that grants nothing); a missing
`permissions` → `invalidRequest`, and so is a missing `isActive` on a staff update (`bool?`), so a forgetful client
can't empty a role or deactivate someone. Staff add/update also answer `nameTooLong`; `roleIds` duplicates are ignored;
`roleNotFound` (400) is checked before `staffExists` (409). Staff search: the full name; a phone-like term also
matches its digits (Arabic-Indic ones mapped to ASCII) without leading zeros inside the stored E.164 phone (`0100…`
finds `+20100…`). There is no GET of one role or
staff member: a 201's `Location` is the list. `StaffMember.roles` are Owner first, then by name. Invalidations as in the
D3 table; a role update always invalidates its role (rename included); nothing user-level is needed when someone loses
their last clinic (the user entry holds only the super-admin flag; contexts are read from the database). The role and
staff use cases live in Access (`Roles/`, `StaffMembers/`, § 9 layout), with pure `RoleRules` / `StaffRules` helpers
(`IQueryable` extensions the handlers compose and run, e.g. `db.Roles.WithName(name).AnyAsync()`; role names compared
case-insensitively: the stored name lowered by the database, the new one with the invariant culture).

```ts
type ClinicSummary = { id: number; name: string; status: "active" | "suspended"; staffCount: number; createdAt: string };
type ClinicDetails = ClinicSummary & { owners: { staffId: number; fullName: string; phone: string }[] };
type Role = { id: number; name: string; isOwner: boolean; permissions: string[]; staffCount: number };
type StaffMember = { id: number; userId: number; phone: string; fullName: string; isActive: boolean;
                     roles: { id: number; name: string; isOwner: boolean }[] };
```

## 7. Errors (new)

| Code | Class | Status | When |
|---|---|---|---|
| `roleNameTaken` | `RoleErrors` | 409 | another role of the clinic has the name |
| `unknownPermission` | `RoleErrors` | 400 | a key not in the catalog |
| `roleLocked` | `RoleErrors` | 409 | editing or deleting the Owner role |
| `roleInUse` | `RoleErrors` | 409 | deleting a role that staff still hold |
| `roleNotFound` | `StaffErrors` | 400 | a `roleIds` entry not in the clinic |
| `rolesRequired` | `StaffErrors` | 400 | no role given |
| `staffExists` | `StaffErrors` | 409 | the phone is already staff in the clinic (active or not) |
| `lastOwner` | `StaffErrors` | 409 | the change would leave no active Owner |
| `nameInvalid` | `CommonErrors` | 400 | a name (any `ValidName()` field: clinics, staff, roles, drugs, groups) contains control characters, e.g. a NUL, or a line/paragraph separator (U+2028/U+2029) (M1.5.2), or a bidi override or isolate (U+202A–U+202E, U+2066–U+2069; M1.5.4: a reversed or look-alike name, and one that can't be typed to confirm a delete; ZWJ/ZWNJ and the plain marks U+200E/U+200F/U+061C stay allowed). A name made only of spaces or invisible format characters is `nameRequired` |
| `invalidText` | `CommonErrors` | 400 | free text (`ValidText()`: a drug's description) contains a NUL (M1.5.2); line breaks and tabs are allowed |

Rule of thumb: 400 = the request itself is wrong; 409 = it conflicts with the current data.
Plus `notFound` (404) for unknown clinics, roles and staff (`ClinicErrors.NotFound`, `RoleErrors.NotFound`,
`StaffErrors.NotFound`, all code `notFound`). All codes get `errors.*` in `en.ts` and `ar.ts`.

## 9. Sub-steps

Each sub-step is one implementation session, validated (build, EF, tsc/eslint, smoke test on :5055) and
committed before the next. No automated tests until M1.6.

**Review cycles (every sub-step, user's rule):** cycle 1 is always **dense**: several parallel agents, at least
validation against this doc, code review, bug hunt, and isolation/security (plus frontend/RTL for M1.5.4–5),
and a **browser test**: an agent drives the real app (API on :5055, built SPA) through the sub-step's flows
and reports what breaks (for the backend sub-steps, the flows that exist in the UI so far, e.g. login and the
catalog still working), then fix. Cycle 2 runs only if cycle 1 found significant issues (scope: the fixed areas and what they touch),
then fix. Cycle 3 runs only if cycle 2 still found significant issues. The risk column sets how many agents
cycle 1 gets.

## 11. Open points (decide during the sub-steps, not blocking)

- Clinic names are not unique (two clinics may share a name); the detail page shows the owners to tell
  them apart (the list could add owner names later).
- Phone shown in staff lists: the full number (super admin only).
- A future "restore deleted clinic" clears `DeletedAt` (the clinic returns with the `Status` it had).
- Who deleted a clinic is not recorded (only when); it comes with the audit log.
- Without session revocation (D7), a removed user's access token still works ≤ 15 min on endpoints outside
  a clinic (`/me`, `/auth/contexts`, `/permissions`); they reveal nothing of the clinic. Accepted.
- Likewise, after a super admin logs out, their platform access token still works on `/admin/*` until it
  expires (≤ 15 min): the `PlatformAdmin` policy checks the super-admin flag, not the session. Accepted (D7).
