# M1.6 Test foundation: design

Status: **approved** (2026-10-15). Step M1.6 of [Phase 1 (MVP)](platform-hld.md#12-delivery-phase-1-mvp).
Built in **four waves** (W0–W3, [§ 7](#7-sub-steps-and-waves)); inside a wave, independent tracks run in parallel.

Builds on: [platform HLD](platform-hld.md) (NFR-7), [backend architecture](architecture.md),
[tech overview](../tech/overview.md), every `docs/features/*/business.md` (the source of the test cases).
Where this document and the HLD differ, this document wins and the HLD is updated with M1.6.

---

## 1. Goal

Turn the documented behavior of M1.1–M1.5 into automated tests that are trusted, fast to run at the right depth,
and kept up to date by every later step.

**Why it matters:** the MVP ends with **one full manual acceptance test by the client**, testing everything, freely.
If it fails, the client won't trust us again. So coverage must be broad (every business rule, every message, both
languages, desktop and phone) and deep where the risk is (isolation, login, permissions, the prescription text).

**Done when:**
- every P0/P1 case of the [test catalog](#d2-test-catalog) has at least one automated test, checked by a script;
- `test.ps1 -Tier full` is green on a clean machine (Docker running) and the coverage gates hold;
- `test.ps1 -Tier release` has a recorded baseline (mutation scores at or above the gates);
- the docs say how to run and extend the tests, and the "no automated tests" lines are gone.

## 2. Decisions already made (user, 2026-10-15)

| Topic | Decision |
|---|---|

| Coverage gates | Our proposal accepted, may be raised: [D5](#d5-coverage-and-mutation-gates) uses the raised numbers |
| CI | **None** for now. Tests run locally through one runner |

| Role names | Not translated, except the **Owner** role's label (§ 5.1) |
| Login messages | Clearer messages after a correct code for a suspended clinic and a deactivated staff member (§ 5.2) |
| Branch | All of M1.6 on branch `m1.6-test-foundation`; parallel tracks in git worktrees branched from it; merging to `main` is the user's call |

## 3. What exists today

- No test projects. Behavior was verified manually per step (see each feature's "Testing notes"); the M1.5 final
  acceptance used Python scripts (a 342-case API matrix, regression and browser seeds) in a session scratchpad.
- Testability already in place: `TimeProvider` is injected where time matters (OTP, sessions, tokens, clinic delete);
  every service is behind an interface; one ProblemDetails shape; config validated at startup.
- Not in place: `Program` is not visible to a test host (`public partial class Program` needed); Application types are
  `internal` (validators, handlers): unit tests need `InternalsVisibleTo` for the test projects.
- The base `appsettings.json` OTP limits are relaxed on purpose (5000 / 0 / 5000) until M3.2. Tests never rely on
  them: they set their own values.

## 4. Decisions

### D1. Branch and worktrees

- `m1.6-test-foundation` is created from `main`. W0 and W3 work on it directly.
- A parallel track gets its own worktree and branch from the M1.6 branch (`m1.6/<track>`), its own scratch database
  (`drags_<track>`), its own API port, and its own test database names (the run id includes the track, [D3](#d3-test-stack-and-layout)).
  Two agents never build the same project in the same folder.
- Shared files (`ClinicHub.sln`, `ClinicHub.Web/package.json`, the runner, the catalog's mapping) are created in W1 by
  the track that owns them; later tracks only add their own files. A conflict goes back to the orchestrator.
- The orchestrator validates each track, merges it into the M1.6 branch (in a fixed order), commits (no push, no AI
  attribution), and the next wave branches from the result.

### D2. Test catalog

`docs/testing/test-catalog.md` (English, with links to the Arabic source sections): one table per feature area.

| Column | Meaning |
|---|---|
| ID | `<AREA>-<NNN>`, stable, never reused: `AUTH`, `ISO` (clinic isolation), `ACC` (access), `ADM` (platform admin), `DRUG`, `GRP`, `DOSE`, `TAPER`, `RX` (prescription), `I18N`, `ERR` (error contract), `UX` (cross-cutting UI: layout, mobile, RTL, double clicks) |
| Case | One behavior, written as "given / when / then" in one line |
| Priority | **P0** acceptance-critical (a client would notice; data/isolation/security), **P1** important rule or message, **P2** edge or cosmetic |
| Level | where it is tested: `unit`, `api` (integration), `ui` (component), `e2e`, `manual` (only when it can't be automated: pasting into Word, Windows Notepad, a real phone) |
| Source | link to the business/tech doc section |

- Every test carries its case IDs (xUnit `[Trait("Case", "AUTH-012")]`, Vitest/Playwright `@AUTH-012` in the title).
  The catalog does **not** keep a "covered by" column by hand: `tests/tools/traceability` lists the IDs found in the
  tests and fails when a P0/P1 case has none (or a test names an unknown ID). Its report goes to `artifacts/`.
- Messages: every user-visible message in the business docs becomes a case (Arabic and English text checked against
  the locale files by an `I18N` test, and shown in at least one e2e test per area).
- Each later step adds its feature's cases to the catalog with the feature.

### D3. Test stack and layout

| Level | Tool | Where |
|---|---|---|
| Backend unit | xUnit, **Shouldly** (MIT; FluentAssertions 8 is commercial) | `tests/ClinicHub.UnitTests` (Domain + Application pure rules: `DosingRules`, `PermissionCatalog`/`PermissionSet`, `PhoneNormalizer`, `ValidName`/`ValidText`, `StaffRules`, `RoleRules`, `SessionRules`, `Paging`, validators) |
| Backend integration | xUnit, `WebApplicationFactory<Program>`, the compose PostgreSQL 17 (`drags-postgres`, a throwaway database per run), **Respawn** to reset between tests, `FakeTimeProvider` | `tests/ClinicHub.IntegrationTests`, grouped by area (`Auth/`, `Isolation/`, `Access/`, `Admin/`, `Catalog/`, `Errors/`) |
| Frontend unit + component | **Vitest** (jsdom), Testing Library, **MSW** for the API in component tests | next to the code: `src/**/*.test.ts(x)` |
| End to end | **Playwright** | `ClinicHub.Web/e2e/`, against the Release API serving the built SPA on its own port and database |
| Mutation | **Stryker.NET** (backend critical modules), **StrykerJS** (frontend pure logic) | release tier only |
| Coverage | coverlet + ReportGenerator; Vitest v8 coverage | reports in `artifacts/` (git-ignored) |

Integration test rules:
- **Database: the existing compose container, not a container per run** (user, 2026-10-15: no CI, and the container is
  always there; Testcontainers only if CI is added later):
  - `test.ps1` runs `docker compose up -d` first and waits for PostgreSQL.
  - Each run (per worktree/track) migrates one template database `drags_it_<run>_tpl` once; each parallel test group
    (xUnit collection) gets its own copy with `CREATE DATABASE drags_it_<run>_<n> TEMPLATE drags_it_<run>_tpl` (fast,
    no migration per group); Respawn resets the data per test class inside a group.
  - The run drops its databases at the end; every run first drops stale `drags_it_*` databases older than a day (left by
    crashed runs).
  - Safety: the test host refuses to start on a database not named `drags_it_*` (never `drags`), and never touches other
    databases.
- Each test builds the data it needs through **test builders that call the real use cases** (e.g. `CreateClinicCommand`), never
  raw inserts, except to simulate "changed outside the app" cases.
- Environment `Testing` with its own settings: the **intended** OTP limits (5 attempts, 60 s, 5 per hour), Display mode,
  test keys; no dev seed (no 10,000 drugs). The startup seeder still creates the template and a test super admin.
- Login helper: the real OTP flow (request → `devCode` → verify → context) with a cookie jar per client, plus a fast
  path that reuses one session per test class.
- Time: `FakeTimeProvider` replaces `TimeProvider.System` (OTP expiry, resend, session lifetimes, refresh grace).
- Access cache: tests prove the **post-commit invalidation** (change → next request, no waiting). The "changed in the
  database by hand applies within 30 s" path is documented, not tested.
- Ported from the M1.5 Python matrix: its 342 cases are re-expressed as xUnit tests with catalog IDs (Python is not
  kept in the repo).

Frontend rules:
- Pure logic first (highest value per minute): `dosing/types.ts` (normalize, errors, merge, same), `dosingText.ts`
  (every Arabic grammar case: 1, 2, 3–10, 11+, 0.5, «طبقة رقيقة», custom, every frequency/duration, eye), `taper.ts`
  (start, add step, total, generator), `prescriptionText.ts` (plain text, HTML, paste HTML),
  `usePrescriptionLines.ts` (per-clinic storage, legacy migration, once-per-eye, other eye, undo), the add-group
  algorithm (ask eye, conflicts, identical skipped, "apply to the rest"), `permissionChoice.ts`, `api/errors.ts`.
- Components with rules: `DosingFields`, `TaperStepsEditor`, `LineEditDialog`, the group editor, `PermissionPicker`,
  `RequirePermission`/`Can`, `DeleteClinicDialog` (typed name), login page states.

End-to-end rules:
- Critical journeys only (each maps to catalog IDs): login → picker → switch → logout; build a prescription from a
  group with "ask eye" and a conflict, edit a line, other eye, reorder, copy (clipboard plain + HTML read back), clear
  + undo; drugs CRUD with dosing and taper; group editor with overrides and the unsaved-changes guard; permission
  gating per default role and a custom role; the full admin flow (create clinic → owner logs in to the copied catalog;
  roles; staff; disable / delete → lockout messages for a user inside the clinic).
- Projects: Chromium desktop 1280 in **Arabic** and **English**, Chromium phone (375 px, touch); Firefox and WebKit
  desktop in the release tier (the client's browser is unknown).
- Every page visited also checks: no horizontal scroll, no console errors, `dir`/`lang` right, and an axe-core scan
  (serious/critical violations fail the full tier).
- Browser contexts keep their own cookies, so parallel users don't log each other out (no `<name>.localhost` trick).

### D4. Tiers and the runner

One PowerShell runner at the repo root (Windows, like `deploy.ps1`):

```
./test.ps1 -Tier step [-Area auth,access]     # ~50–60%: all unit + smoke + the listed areas (default: from git diff)
./test.ps1 -Tier full                         # everything + coverage gates + traceability
./test.ps1 -Tier release                      # full + mutation + Firefox/WebKit e2e
```

- Tags: xUnit traits `Area` and `Tier` (`Smoke`), Vitest/Playwright title tags `@smoke`, `@area:auth`.
- `step` picks the areas from `git diff` against the branch point (folders → areas map in the runner) unless `-Area`
  is given; it always runs all unit tests (they take seconds).
- Smoke = one happy path per area + the top P0 cases; target ≤ 3 minutes.
- When each runs: `step` after every implementation/fix round; `full` at the end of a feature/milestone, before merging
  to `main`, and before the dress rehearsal; `release` at milestone ends and before launch.
- The runner writes one summary (passed/failed per level, coverage, traceability, mutation) to `artifacts/summary.md`.

### D5. Coverage and mutation gates

Raised from the first proposal (user allowed higher). Enforced in `full` (coverage, traceability) and `release`
(mutation); a gate miss fails the tier.

| Scope | Gate |
|---|---|
| Backend, overall (Domain + Application + Infrastructure + Api, excluding migrations and generated code) | lines ≥ **90%**, branches ≥ **85%** |
| Backend critical: clinic filter + interceptor, `Identity/Login`, `Identity/Sessions`, `Access/Authorization`, `Access/Roles`, `Access/StaffMembers`, `Platform/*`, `Api/Features/Access`, `AdminClinicFilter` | branches ≥ **95%**, Stryker mutation score ≥ **85%** |
| Frontend pure logic (§ D3 list) | lines ≥ **95%**, branches ≥ **90%**, StrykerJS mutation score ≥ **85%** |
| Frontend components and pages | no percentage gate; covered by catalog traceability + e2e |
| Catalog | **100%** of P0 and P1 cases mapped to a test; P2 ≥ 80% |

Gates may only go up later; a lowered gate needs the user's OK.

### D6. Rule parity between C# and TypeScript

The dosing/taper rules exist twice (`DosingRules` and `features/dosing/types.ts` + `taperConfig.ts`). One fixture file,
`tests/fixtures/dosing-cases.json` (input, valid?, normalized), is run by **both** xUnit and Vitest, so the two can't
drift. Vitest also checks the expected Arabic sentence of each valid case.

### D7. What stays manual

Pasting into Word (formatting kept) and Windows Notepad (plain text), a real phone, the real HTTPS deployment, SMS (not
built). They are `manual` cases in the catalog and part of the dress rehearsal checklist.

### D8. Dress rehearsal (defined now, run at the end of M3.2)

A production-like run before the client's test: Production config, the target server size, HTTPS, a fresh database,
realistic data (Arabic names, hundreds of drugs, several clinics), desktop and phone, Arabic and English. Agents act
as the client: the full catalog by hand plus free exploration, every finding fixed and re-run until a clean pass. The
checklist lives next to the catalog (`docs/testing/dress-rehearsal.md`).

### D9. Bugs found while writing tests

Changed by the user after W0 (2026-10-15): **W1–W3 don't fix app code; bugs are collected and fixed after M1.6.**

- A test that fails because the app is wrong (the doc is the rule, quoted): the test stays as written (never weakened
  to pass), is marked as a known bug (xUnit `Skip = "BUG-012: …"` / Vitest and Playwright `test.fixme` with the same
  ID) and the bug is added to `docs/testing/known-bugs.md` (ID, case IDs, doc line, what happens, how to reproduce,
  severity). The orchestrator checks each entry (app vs doc) before it is accepted.
- Known-bug tests don't count against the gates (traceability counts their cases as covered-but-failing and lists them
  in the summary); the list is reported at the end of every wave.
- After M1.6: the bugs are fixed one per commit, each unmarking its tests (they must then pass).
- A rule the docs don't settle → it goes to the user's question list (not a bug), the case keeps today's behavior.

### D10. Review of test code

Each track's review cycle checks, besides code quality: every test asserts a **business** outcome (status, code,
message, data), not an implementation detail; no sleeps (time via `FakeTimeProvider`, waits via Playwright
assertions); tests are independent (run in random order, run 3× for flakiness); a planted-bug spot check (break one
rule, the suite must fail).

## 5. Behavior changes and fixes before the tests (M1.6.0)

Done first so the tests lock the final behavior. Each with its docs (business + tech, both languages for UI strings).

### 5.1 Owner role label translated

- Role names stay data (not translated). Only the **Owner** role (`IsOwner`) is shown with a translated label wherever a
  role name appears: role list, staff role chips, staff editor, the `lastOwner` message, `/me` roles shown in the UI.
  English "Owner", Arabic «المالك». The stored name stays `Owner`.
- `admin.create.templateNote` in `ar.ts` names the default roles in Arabic «(المالك، الطبيب، المساعد)» while Doctor
  and Assistant show in English: align it with what is shown.
- Open point (§ 9): reject a new role named like the Owner label in either language («المالك» / "Owner"), so two
  roles never look the same.

### 5.2 Clearer messages at login

The message appears only **after a correct code**, so once SMS exists only the phone's owner sees it; it reveals
nothing to someone guessing numbers. When the user has no place left to enter:

| Situation | Code | Message (en / ar) |
|---|---|---|
| Staff only in suspended clinic(s) | `clinicSuspended` (existing) | the clinic is suspended, with its name |
| Staff deactivated (in an active clinic) | new `staffInactive` (403) | "Your account in “{{clinic}}” is deactivated. Ask the clinic owner." / proposal «تم إيقاف حسابك في «اسم العيادة». تواصل مع مالك العيادة.» |
| Deleted clinic, removed staff, unknown phone | `noAccess` (unchanged) | the generic message (a deleted clinic is never revealed) |

Several reasons at once: suspended first, then deactivated, else `noAccess`. The same reasons apply in the clinic
picker when a picked clinic can't be entered. Exact wording approved by the user in W0.

### 5.3 Fix: one drug per eye in a group uses the effective eye (review finding CAT-D13)

Today the server checks duplicates on the line's own eye only; after a drug's default eye changes, a group can hold
the same drug twice for one eye, and adding it to a prescription silently drops the second line. Fix: the group save
checks the **effective** eye (override eye, else the drug's default eye) in the handler (`duplicateGroupItem`); the
group editor marks clashing lines; adding such a group to a prescription reports the dropped line in its summary toast
instead of dropping it silently.

### 5.4 Fix: a switch with an ended session must not clear another session's cookie (review finding AUTH-T01)

`POST /auth/context` with an ended session's access token clears the refresh cookie even when the cookie belongs to
another, live session (e.g. log out in one tab, log in again in another, then use the stale tab). Fix: clear the cookie
only when it belongs to the ended session.
