## Migration `RenameGroupsToProtocols`

Added on top of `AddSearchNames` with `dotnet ef migrations add RenameGroupsToProtocols --project
ClinicHub.Infrastructure --startup-project ClinicHub.Api` (never regenerate; the snapshot is updated by that command,
not by hand). The model already has the new names, so the scaffold is the starting point; **rewrite its body** so it
only renames (EF scaffolds drop/add for keys and FKs): `RenameTable`, `RenameColumn`, `RenameIndex`, and
`ALTER TABLE … RENAME CONSTRAINT` through `migrationBuilder.Sql` for PK/AK/FK (renaming a PK or AK constraint also
renames its index). Never `DropTable`/`CreateTable`, `DropForeignKey`/`AddForeignKey`, `DropPrimaryKey`/`AddPrimaryKey`.
After it, `dotnet ef migrations has-pending-model-changes` must say none.

Every name, read from `AppDbContextModelSnapshot.cs` and `20261011172641_Initial.cs`:

| Kind | Old | New |
|---|---|---|
| Table | `DrugGroups` | `Protocols` |
| Table | `DrugGroupItems` | `ProtocolItems` |
| Column (`ProtocolItems`) | `DrugGroupId` | `ProtocolId` |
| PK | `PK_DrugGroups` | `PK_Protocols` |
| AK (unique constraint) | `AK_DrugGroups_Id_ClinicId` | `AK_Protocols_Id_ClinicId` |
| FK | `FK_DrugGroups_Clinics_ClinicId` | `FK_Protocols_Clinics_ClinicId` |
| Index | `IX_DrugGroups_ClinicId_Name` | `IX_Protocols_ClinicId_Name` |
| PK | `PK_DrugGroupItems` | `PK_ProtocolItems` |
| FK | `FK_DrugGroupItems_Clinics_ClinicId` | `FK_ProtocolItems_Clinics_ClinicId` |
| FK | `FK_DrugGroupItems_DrugGroups_DrugGroupId_ClinicId` | `FK_ProtocolItems_Protocols_ProtocolId_ClinicId` |
| FK | `FK_DrugGroupItems_Drugs_DrugId_ClinicId` | `FK_ProtocolItems_Drugs_DrugId_ClinicId` |
| Index | `IX_DrugGroupItems_ClinicId` | `IX_ProtocolItems_ClinicId` |
| Index | `IX_DrugGroupItems_DrugGroupId_ClinicId` | `IX_ProtocolItems_ProtocolId_ClinicId` |
| Index | `IX_DrugGroupItems_DrugId_ClinicId` | `IX_ProtocolItems_DrugId_ClinicId` |
| Identity sequence (not in the EF model) | `DrugGroups_Id_seq` | `Protocols_Id_seq` |
| Identity sequence (not in the EF model) | `DrugGroupItems_Id_seq` | `ProtocolItems_Id_seq` |

The two identity sequences are PostgreSQL's implicit names (`<table>_<column>_seq`); `RenameTable` keeps the old
ones. Rename them too (`ALTER SEQUENCE "DrugGroups_Id_seq" RENAME TO "Protocols_Id_seq"`, same for the items) so a
migrated database matches a fresh one; nothing in the app reads them. The stored `SearchName` column, the owned
`Dosing_*` columns and every other column keep their names. The FK `FK_ProtocolItems_Drugs_DrugId_ClinicId` is
renamed here and dropped later by `AddSharedCatalog` (M1.7b).

Permission rows (D10), in the same migration after the renames:

```sql
-- Up
UPDATE "RolePermissions" SET "Permission" = 'protocols.' || substr("Permission", 8) WHERE "Permission" LIKE 'groups.%';
-- Down
UPDATE "RolePermissions" SET "Permission" = 'groups.' || substr("Permission", 11) WHERE "Permission" LIKE 'protocols.%';
```

`RolePermissions` is the only place permission keys are stored (PK `RoleId, Permission`); every clinic's roles move
(deleted clinics and the template included: no `ClinicId` filter). Only keys starting with `groups.` change; a role
can't hold a `protocols.*` key before the migration, so no duplicate is possible (ACC-088). The Owner role has no
rows (every permission). Down reverses the renames in the opposite order, then the permission rows. The migration is
tested up → down → up with data (ACC-085, ACC-088; migration collection on the bare template).

## Old API routes

Today (`Program.cs`): `app.UseProblemStatusCodePages()` plus `MapFallbackToFile("{*path:regex(^(?!api(/|$))):nonfile}",
"index.html")`. The SPA fallback is a GET endpoint whose constraint refuses `/api/…`, so for any unknown `/api` path
(ERR-015, ERR-016, ERR-018):

| Method | Answer |
|---|---|
| GET | 404 ProblemDetails, code `notFound` |
| POST, PUT, DELETE, PATCH | 405 ProblemDetails, code `methodNotAllowed` |

Removing `DrugGroupsController` (done here) is therefore enough for GRP-101: `/api/v1/drug-groups`,
`/api/v1/drug-groups/{id}` and `/api/v1/drugs/{id}/groups` answer 404 `notFound` for GET and 405 `methodNotAllowed`
for POST, PUT and DELETE. No alias, no new code; only the test. In the SPA (GRP-105), an old bundle's GET gets
`errors.notFound` («هذا العنصر لم يعد موجودًا.» / "This item no longer exists."), its saves get `errors.generic`
(«حدث خطأ ما. حاول مرة أخرى.» / "Something went wrong. Please try again.": `methodNotAllowed` has no key on purpose).
